# GH-63 - Evaluate and integrate Cloudflare's security-audit methodology into Vulnerability Hunter

## Context
The vulnerability hunt already plans lanes in a preflight, hunts read-only, has High and Medium findings refuted by a separate verifier and writes one authoritative SECURITY-REPORT.md. Cloudflare's public `security-audit` skill describes a stricter multi-stage audit: reconnaissance of trust boundaries, a machine-readable coverage ledger, a coverage critic, fresh-agent adversarial validation, schema-validated findings with distinct verdict states, and reports generated from the verified records. This task compares the two in detail, records an adopt/adapt/reuse/reject decision per practice, and implements only the parts that improve the verdict inside the existing preflight, lanes, findings and run-record lifecycle, without weakening the read-only, sandbox, network, prompt-injection and secret-handling boundaries, without a runtime dependency on Cloudflare's repository, and with agent budgets proportionate to a focused or a full audit.

## Definition of Ready
- [ ] The spec holds the feature-by-feature gap analysis and the adopt/adapt/reuse/reject decision with rationale for each Cloudflare practice

## Definition of Done
- [ ] The adopted changes extend the existing hunt (preflight, lanes, verifier, findings, report, run records) and do not create a parallel audit system
- [ ] Confirmed, unresolved and rejected verdicts stay distinct, verification stays independent of discovery, and every security boundary of the hunt is kept or made stronger
- [ ] Tests cover the validators, malformed or inconsistent findings, incomplete runs and missing sandbox or tool capabilities; skill changes carry before/after evidence through `ultrapowers:writing-skills`, and the offline suites pass
- [ ] The documentation names which Cloudflare concepts or components were adopted, with provenance and any MIT notices
