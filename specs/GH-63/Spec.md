# GH-63: Cloudflare's audit practices in the vulnerability hunt

Status: draft, 2026-10-30. Ticket: GH-63.

## Intent

A developer, or the Owner, runs `/ultrapowers:vulnerability-hunt` on a ticket or on a whole repository before a merge or a release, or task-review runs it at its Step 3b. Today the hunt leaves `SECURITY-REPORT.md` and `security-findings.json`, but nobody can tell from them what was examined: a lane block that says `ok` proves nothing, a candidate below confidence 6 or of Low severity is never judged, and the records can drift from the contract with no check until task-review cannot read them. Cloudflare published the skill that seeded its vulnerability harness. The Owner wants its strongest practices in the hunt, adapted to the hunt's read-only design and its harnesses, as one complete migration: the old record shapes, the old verdict code and every piece of the current implementation that the new design replaces are removed, not kept beside it.

Success, for the person who reads the report: every claim traces to a record that a script validated; a coverage ledger shows every in-scope file and every mapped surface as covered, blocked, not covered or not applicable, each with its evidence or its reason; every candidate a hunter raised was judged by an agent that did not raise it; a candidate ends `confirmed`, `needs-validation` or `rejected`, and only `confirmed` carries a severity; the verdict never reads PASS while a lead is open, a candidate is unjudged or a gap is left; and the repository holds no dead code, no unused code and no unused dependency from the implementation it replaced.

## Goals, non-goals and anti-goals

Goals:
- a coverage ledger per run, `reviews/<ID>/coverage-ledger.json`: file units seeded from the preflight's saved scope by fixed rules per lane, surface units from a recon step and from the critics, each closed with evidence or left with a reason;
- every gap hunted: after each wave a script check and a fresh critic; follow-up waves until both find nothing, at most `hunt.maxFollowUpWaves` of them (default 3);
- secrets found by a tool first: gitleaks, when it is installed, runs read-only with redaction over each repository and its history as an audit tool of the secrets lane; the hunter's recorded searches are the fallback;
- every candidate judged: one verifier per High or Medium candidate, batch verifiers per lane (at most 25 items each) for its leads below confidence 6 and its hardening notes, and a verifier of its own for every item a batch verifier promotes;
- three verdict states with distinct fields: `needs-validation` has no severity, and a `rejected` record keeps its trace and its reason;
- a stable finding id (`findingId`; Cloudflare calls it a fingerprint) that the script builds from fixed parts, so that verifications, duplicates and the report match by id, never by title;
- every agent block saved verbatim under `reviews/<ID>/blocks/`, and every record file built from those blocks by `skills/vulnerability-hunt/scripts/check-hunt.mjs`, which validates them and checks every cited file and line mechanically;
- the verdict computed once, in `skills/vulnerability-hunt/scripts/hunt-records.mjs`, which task-review's assembler imports, and `SECURITY-REPORT.md` rendered from the records by the script;
- a hunt INCOMPLETE makes the task review BLOCKED;
- Cloudflare's 11 attack-class files vendored verbatim under `skills/vulnerability-hunt/references/cloudflare/`, with their MIT notice and their provenance, and each hunter given only the blocks its units select;
- a complete migration: no dead code, no unused code, no unused export, no unused import and no unused dependency left from the current implementation, proved by a test;
- documentation of the resulting workflow, its limits, and which Cloudflare concepts and files were adopted.

Non-goals:
- running target code in any sandbox: the hunt stays read-only and runs no project code; a decisive fact that needs execution makes the lead `needs-validation` (D9);
- Cloudflare's artifact promotion procedure: nothing runs, so nothing is promoted (D9);
- carrying findings or coverage over from an earlier run: decision 6 of `docs/ultrapowers/specs/2026-10-11-vulnerability-hunt-design.md` ("Baseline: None") stands; a later ticket can take it (D9);
- Cloudflare's run profiles (`quick`, `standard`, `deep`) and its agent budget gate: the hunt keeps its ticket and full-audit modes and records its spend (D9);
- a second verification pass over the final records, Cloudflare's Phase 5 (D4);
- the fleet features of the blog: dedup agents, the wishlist, cross-repo tracing, a database (D9);
- vendoring Cloudflare's `SKILL.md`, `RECONNAISSANCE.md`, `HUNTING.md`, `VALIDATION-AND-REPORTING.md`, schema or validators: the hunt's prompts and checker are written in its own words, modelled on them (D6);
- reading a findings file written before this change: task-review refuses it and asks for a new hunt (D10);
- an autopilot hunt stage: issue #43;
- a version bump or a release: a separate step under AGENTS.md Rule 6.

Anti-goals:
- a second audit system beside the hunt, or a second verdict rule that can disagree with the first;
- old code kept "for compatibility" beside the new code: a second reader, an unused export, a dead branch, an orphaned test or a prompt field nobody reads;
- a vendored block that leads a hunter to run a test, a build, a fuzzer or any project code;
- a report or a PASS that claims coverage the ledger does not show;
- a `needs-validation` lead with a severity, or hardening advice shown as a vulnerability;
- a verifier that judges its own hunter's work, or that sees another verifier's conclusion;
- an agent that hand-edits a record file instead of saving its block for the script to fold;
- a hunter prompt that carries whole reference files instead of its selected blocks;
- a secret value or a hash of one in any record, ledger, script output or report, and any hunt document that asks for a "fingerprint".

## Decision record

### D1: extend the hunt in place
- **Chosen:** every adopted practice lands inside the hunt's STEP 0 to STEP 5, its five lanes, its run record and its output files. The preflight saves its scope; `check-hunt.mjs seed` turns it into file units; one recon agent maps the surfaces and selects the vendored blocks; the hunters close units and return candidates; after each wave the script folds the saved blocks and a fresh critic looks for gaps, with at most 3 follow-up waves; the verifiers judge every candidate; `check-hunt.mjs` validates the records, computes the verdict and renders the report; the vendored attack-class files sit under `skills/vulnerability-hunt/references/cloudflare/`.
- **Why this one:** it meets the acceptance criterion that adopted improvements "integrate with existing preflight, lanes, findings, and run-record lifecycle rather than creating a parallel audit system". Evidence: `tasks/GH-63/source.md:122`. The Owner chose it twice in this conversation ("A: extend in place", then "Approach A looks good for me"). Evidence: the Owner, in this conversation.
- **Rejected:** a separate `--deep` mode that runs Cloudflare's six phases as written, because it is the parallel audit system the acceptance criteria rule out and it needs the OS sandbox no harness proves to the hunt. Evidence: `tasks/GH-63/source.md:122`; Cloudflare's `SKILL.md`, "Universal execution safety".
- **Rejected:** changes to the prompts only, because records guarded by prose alone drifted until task-review could not read them. Evidence: this session's probe, `decideSecurity` throws on `reviews/audit-2026-10-11/security-findings.json` ("unknown verdict \"unverified\"").
- **Failure points:** the cost grows with the critic loop and the batch verifiers. Mitigation: the 3-wave stop (D3), batches of at most 25 items (D4), `hunt.maxHuntersPerLane` per wave, the fixed seed rules (D3), and the agent counts in the report. Evidence: the Hacker News thread on item 49736466 (summarised by the fetch tool) reports token cost on whole-repository runs; `reviews/audit-2026-10-23` used 1 research step, 12 hunters and 34 verifiers.
- **Failure points:** the contract outgrows its 300-line limit. Mitigation: the detail of each new step lives in its own prompt file (`prompts/recon.md`, `prompts/critic.md`, `prompts/lead-verifier.md`) and in the script's printed instructions; the contract names the step, its inputs and its outputs. Evidence: `tests/vulnerability-hunt/test-skill-structure.sh:196`; the agent file has 250 lines.
- **Edge cases:** the inline form, with no subagent tool. The session runs the recon step, the lanes, the critic and the verifiers itself and saves each block the same way; `blocks/run.json` says `"inline": true`, every verification is folded with `independent: false`, and the report says no step was independent. Evidence: `agents/vulnerability-hunter.md:222-228` (the inline form today). My call: such a run can still read FAIL or PASS-WITH-ISSUES, as today, because the inline form exists for harnesses that cannot do better.

### D2: verdict states, finding ids, hardening and the verdict rule
- **Chosen:** a candidate ends in one of three states. `confirmed`: the verifier walked the whole trace and found no control; it carries `severity` (`High` or `Medium`), `confidence`, `principal` (the lower-trust actor), `boundary` (the control it crosses), `impact` (the affected resource and the concrete result), `trace`, `exploit`, `mitigationExamined` and `fix`. `needs-validation`: the trace holds but a decisive fact is not visible in the repository or needs code to run; it carries `blockers` (at least one, each the exact missing fact) and `validationPlan` (`deployment`: what the owner observes; `execution`: the bounded check the owner could run in their own sandbox, described and never run by the hunt; at least one of the two), and never a `severity`, an `exploit` or a `fix`. `rejected`: the trace breaks, a control stops it or an exclusion applies; it keeps `trace` and carries `reason` with the `file:line` that proves it, and never a `severity`, an `exploit` or a `fix`. The script removes the hunter's `severity`, `exploit` and `fix` from a record whose state is `needs-validation` or `rejected`, so only a `confirmed` record carries them. Low stops being a severity: what was a Low finding is a `hardening` note (`file`, `line`, `symbol`, `category`, `title`, `note`), reported in its own section, never counted. A `trace` is an array of steps `{ kind, file, line, description }`, `kind` one of `entrypoint`, `propagation`, `sink`, the first `entrypoint`, the last `sink`, `propagation` only between (a one-step trace is `entrypoint` or `sink`); it replaces the `attackPath` string. Every candidate, lead and hardening note carries `file` and `symbol`: the location of the fix, the sink or the missing control (the function, route, configuration key or step where the control belongs), never an entry point; the entry points are the `entrypoint` steps of its `trace`, so two routes that reach one unsafe helper give one id. It also carries `category` from a closed list: `injection`, `command-execution`, `path-traversal`, `authentication`, `authorization`, `tenant-isolation`, `data-exposure`, `deserialization`, `ssrf`, `xss`, `csrf`, `crypto`, `secret`, `supply-chain`, `pipeline`, `dependency`, `prompt-injection`, `tool-misuse`, `memory-manipulation`, `mcp-config`, `logic`, `other`. The script builds `findingId` as `<repo>:<file>:<symbol>:<category>`, lowercased, each part with every character outside `[a-z0-9._/@+-]` replaced by `-`, matching `^[a-z0-9][a-z0-9._:/@+-]*$`; it never holds a line number, a wave, an agent, a severity or a verdict. Two blocks that give the same `findingId` are one candidate listing both lanes; two that share repository, file and symbol but differ in category are printed as possible duplicates, and the gatekeeper merges them only by saving a merge block with its reason.
- **Why this one:** the Owner chose "No severity, never PASS" for an unresolved lead. Evidence: the Owner, in this conversation. The ticket asks to "keep confirmed vulnerabilities, unresolved evidence-backed candidates, and rejected candidates distinct" and not to "present hardening advice as a vulnerability". Evidence: `tasks/GH-63/source.md:72`. Cloudflare's schema forbids severity on `needs_validation`, keeps `trace` and `reason` on `rejected`, and orders a trace from `entrypoint` to `sink`. Evidence: `report-schema.json` at `c1c8a8c`. Title matching loses a verification when a title changes. Evidence: `skills/task-review/scripts/assemble-review.mjs:219`. A free-text id from each hunter would not match across lanes, so the script builds it from fixed parts. Evidence: the builder check of this spec. An id anchored at the entry point would give one unsafe helper as many ids as it has callers; Cloudflare's fingerprint is a root-cause key, and the Owner chose the sink anchor in this conversation. Evidence: `HUNTING.md`, "Candidate gate" rule 6 ("the same source-derived fingerprint for the same root cause"); the Owner, in this conversation.
- **Rejected:** keeping `plausible` with its severity, and a High `plausible` that FAILs, because the Owner chose otherwise. Evidence: the Owner, in this conversation.
- **Rejected:** the field name `fingerprint`, because the structure test fails any hunt document holding that word, so that no agent is ever asked to fingerprint a secret. Evidence: `tests/vulnerability-hunt/test-skill-structure.sh:92-97`.
- **Rejected:** Cloudflare's five-level severity object (likelihood, impact, overall), because the hunt's verdict rule and task-review's rule rest on High and Medium. My call: the vendored blocks' anchors map to the hunt's scale, critical and high to `High`, medium to `Medium`, low and informational to a `hardening` note.
- **Failure points:** the verdict rule becomes: FAIL on a `confirmed` High, a critical or high CVE in a runtime dependency, or an `applies` research advisory of that kind; PASS-WITH-ISSUES on a `confirmed` Medium, a moderate runtime CVE, a critical or high test-only CVE, the research equivalents, or any `needs-validation` record; INCOMPLETE when the dependencies lane produced no block or its status is `incomplete` with no CVE recorded, when any candidate, lead or hardening note is `unjudged`, or when any unit is left `planned`, `blocked` or `not-covered`; PASS otherwise. The ranking stays FAIL, then PASS-WITH-ISSUES, then INCOMPLETE, so a run with an unjudged High and a confirmed Medium reads PASS-WITH-ISSUES; the sentence after `Verdict:` then also names the unjudged items and the uncovered units. My call: the ranking is today's (`agents/vulnerability-hunter.md:204-212`).
- **Edge cases:** a verifier that lowers a High to a Medium. It may, with the reason in `reason`; it never raises a severity: a higher one is a new candidate. My call. A hunter that fills a `severity` on a lead, or a category outside the list: `fold` reports the block and the gatekeeper sends it back once. Evidence: Cloudflare's validator message "needs_validation finding must not contain" (`validate-findings.cjs`).

### D3: the coverage ledger, its seed rules and the critic loop
- **Chosen:** `reviews/<ID>/coverage-ledger.json` is `{ "schema": 2, "id", "maxFollowUpWaves", "units": [] }`; `maxFollowUpWaves` is `hunt.maxFollowUpWaves` of `.agents/ultrapowers.json` at `seed` time (default 3). The units are of three kinds. A **file unit** is one file for one of the three lanes that read files; its status is derived from the hunter blocks. A **reported unit** is one manifest of the dependencies lane or one query family of the osint lane (`dependabot-alerts`, `secret-scanning-alerts`, `code-search`, `osv-scanner`, as `lane-osint.md:25-28` names them); its owning hunter reports a result for it. A **surface unit** is one entry surface and trust boundary with its selected and excluded blocks, added by the recon step or by a critic for the code, secrets-supply-chain or ai-surface lane; its owning hunter reports a result for it. `check-hunt.mjs seed` writes the file and reported units from `reviews/<ID>/preflight.json`, for the lanes the preflight runs only, by these fixed rules. For every lane, a file is `not-applicable` when it is binary (a NUL byte in its first 8,192 bytes, reason "binary file"), when it lies under the project root's `reviews/` (reason "the hunt's own output folder"), or when the key-material rule of the guardrail matches its path (reason "key material: reported by name and kind"). The **code** lane seeds every other in-scope file, except documentation (extensions `.md`, `.markdown`, `.rst`, `.txt`, `.adoc`, and the names `LICENSE`, `NOTICE`, `COPYING` with any extension) and test-only files (a folder segment `test`, `tests`, `__tests__`, `fixtures`, `__fixtures__` or `testdata`, or a file name matching `*.test.*`, `*.spec.*`, `test_*.py`, `*_test.py` or `*_test.go`), which are `not-applicable` with the precedent as the reason. The **ai-surface** lane seeds only the in-scope files with an AI signal (the per-file test of `aiSurfaceSignals` in `hunt-preflight.mjs:352`) and the agent configuration files of the repository whatever the scope (`.mcp.json`, `mcp.json`, `claude_desktop_config.json`, `gemini-extension.json`, `hooks.json`, `plugin.json`, `marketplace.json`, and `settings.json` or `settings.local.json` in a folder whose name starts with a dot). The **secrets-supply-chain** lane seeds every other in-scope text file, plus every manifest and lockfile and every pipeline file of the repository whatever the scope (`.github/workflows/*.yml` and `*.yaml`, `.gitlab-ci.yml`, `Jenkinsfile`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`, `.circleci/config.yml`, `.travis.yml`, `Dockerfile`, `Dockerfile.*`, `*.Dockerfile`, `docker-compose*.yml` and `*.yaml`, `compose*.yml` and `*.yaml`, and a script whose name holds `install`, `release`, `publish` or `deploy` with extension `.sh`, `.ps1`, `.cmd`, `.bat`, `.mjs`, `.js`, `.py` or none). A code or ai-surface file unit is `covered` when any block of its lane lists the file in `filesRead`. A secrets-supply-chain file unit is `covered` when a gitleaks `dir` run recorded in the lane's `tools` (D13; exit 0 or 1, with the path it scanned in `command`) scanned a path that contains the file, or, with no gitleaks run, when a recorded search of its lane (`searches`: the exact command, its exit code, the paths it searched and the `file:line` of each match, never the matched text) covered a path that contains the file; in both cases, when the file has a gitleaks finding or a match, or is a manifest, a lockfile or a pipeline file, the file is also in `filesRead`. A file unit is `blocked` when a block lists it under `blocked` (a file the hunter could not read, with the reason) and no block covered it. Each unit records `id` (deterministic: lane, repository and canonical reference, never a wave, an agent, a verdict or a line), `kind`, `lane`, `repo`, `files`, `origin` (`preflight`, `recon` or `critic`), `wave`, `status`, `owner`, `filesRead`, `checks`, `findingIds`, `unresolved`, `reason` and `attempts`. The state table: `planned` has no owner and no evidence; `covered` has an owner and files read (and, for a reported or surface unit, at least one check of `{ invariant, result }`) and no finding id; `candidate` has the same and at least one finding id; `blocked` has an owner, partial evidence and at least one unresolved fact; `not-covered` and `not-applicable` have no owner and a reason. After each wave the gatekeeper saves every returned block and runs `check-hunt.mjs fold`, which rebuilds the ledger from the seed and the saved blocks, lists the open units and prints the next wave's hunter groups: per lane at most `hunt.maxHuntersPerLane` groups, units in id order, a group closed early when its selected blocks would pass 40,960 bytes. Wave 1's groups follow the preflight's PLAN rows. Then one fresh critic, on the most capable model, reads `architecture.md`, the ledger and the open list, and returns missing surface units and units to reassign; the gatekeeper saves its block and runs `fold` again. The loop ends when `fold` lists no open unit and the latest critic accepted nothing. After the last allowed wave (wave 1 plus `maxFollowUpWaves`; wave 4 by default) and its critic, every unit still open becomes `not-covered` with the reason "wave limit reached (`hunt.maxFollowUpWaves` = `<n>`)".

### D13: gitleaks as an audit tool of the secrets lane
- **Chosen:** the preflight's TOOLS section detects `gitleaks` (`gitleaks version`, like the other tools; `absent` when it does not run). When present, the secrets-supply-chain hunter runs it before it reads: `gitleaks dir <repo path> --no-banner --redact --report-format json --report-path <ROOT>/reviews/<ID>/gitleaks-<repo>-dir.json` over the repository's tree, and `gitleaks git <repo path> --no-banner --redact --report-format json --report-path <ROOT>/reviews/<ID>/gitleaks-<repo>-git.json` over its history, each with `--config <repo path>/.gitleaks.toml` when that file exists. Both runs go into the lane block's `tools` (name, version from TOOLS, exact command, exit code, first 20 lines of stdout). Exit 0 is a clean run, exit 1 a run with findings; any other exit is a failed run, recorded, and the lane falls back to its searches. Each finding of the JSON report becomes a lead or a candidate by its `File`, `StartLine`, `RuleID` and `Commit` fields: a credential still in the tree is a High candidate (category `secret`, symbol the rule id), one only in history a High candidate too (a committed secret is a suspected leaked credential to rotate, as today); the `Secret`, `Match` and `Fingerprint` fields of the report are never copied into a block, a record or the report, and the hunter opens a flagged file only to confirm the kind. A record from the history run carries `commit` (the commit id from the report); the script does not apply the tree line check to it, because the file may be gone from the tree, and the report names the commit. The guardrail allows exactly these forms: the programs `gitleaks` with the verbs `dir`, `git`, `version` and `help`; flags `--no-banner`, `--redact` (required), `--no-color`, `-v`, `--verbose`; valued flags `--report-format` (`json` only), `--report-path` (a path under `reviews/<ID>/`, as `osv-scanner --output` is judged), `--config` and `-c` (a file inside the project), `--log-level`, `--max-target-megabytes`, `--exit-code`; the positional path inside the project; refused: `stdin`, `completion`, `--baseline-path`, `--diagnostics`, `--report-template`, `--enable-rule`, `--gitleaks-ignore-path`, `--ignore-gitleaks-allow`, `--max-archive-depth`, `--max-decode-depth`, and a form without `--redact` (a secret value would reach stdout). `gitleaks` joins `HUNT_AUDIT_TOOLS` in `hooks/lib/qa-shell-writes.mjs`. The report files under `reviews/<ID>/` are run output like the hunters' blocks: `fold` validates that a gitleaks report it reads holds no `Secret` or `Match` field with content (the redaction makes them `REDACTED`), and the gatekeeper deletes nothing. With gitleaks absent, the lane runs as D3 describes, with its searches, and the report names the missing tool.
- **Why this one:** the Owner chose it in this conversation. Evidence: the Owner, in this conversation. This repository already scaffolds `.gitleaks.toml` and runs gitleaks in its pre-commit hook, pinned at v8.30.1. Evidence: `.githooks/pre-commit:3-21`, `templates/.gitleaks.toml.tmpl`. A tool the hunt installs nothing for and that redacts its own output is stronger and more deterministic than a hunter's regular expressions, and the hunt's rule is already "through the audit tools the user installed". Evidence: `agents/vulnerability-hunter.md:28-30`. gitleaks has the `dir` and `git` commands, `--redact` (default 100%), `--report-format json`, `--report-path`, `--no-banner`, and exits 1 on leaks. Evidence: the gitleaks README at `master` (2026-10-28), "Usage"; latest release v8.30.1 (2026-03-21), MIT.
- **Rejected:** gitleaks `stdin` and `--report-template`, because the first reads what a hunter pipes (the shell rules never see that text) and the second runs a template; `--baseline-path`, because a baseline hides findings. My call.
- **Rejected:** making gitleaks required, because a hunt on a machine without it must still run; absence is a note and the searches remain. Evidence: `agents/vulnerability-hunter.md:71` (no manifest is a note, not a failure).

## Architecture

Eight units, in the order a run uses them:

1. **The preflight** (`hunt-preflight.mjs`): as today, plus `--save`, which writes its whole result to `reviews/<ID>/preflight.json` when the status is READY, `gitleaks` in TOOLS, and the export of `chunkInOrder`.
2. **The records module** (`hunt-records.mjs`): the block and record shapes, the category list and the `findingId` rule, the seed rules, the fold, the ledger state table, the mechanical source checks, the verdict rule (`judgeHunt`) and the renderers (the report and task-review's hunt section). It is the one place these rules live.
3. **The checker** (`check-hunt.mjs`): the command-line door to the records module for the gatekeeper (`seed`, `blocks`, `fold`, `final`, `render`).
4. **The vendored references** (`references/cloudflare/`): read through `check-hunt.mjs blocks`; never edited.
5. **The prompts**: the five lane prompts (new return shape, precedence sentence, selected blocks), `verifier.md` (three decisions, `newLead`), and the new `recon.md`, `critic.md` and `lead-verifier.md`.
6. **The contract and the door** (`agents/vulnerability-hunter.md`, `SKILL.md`): STEP 0 to STEP 5 name the new steps, the scripts they run and the files they save.
7. **The consumers**: task-review's assembler, its skill and its template (D10).
8. **The guardrail** (D11): the script list and the shared key rule.

Interfaces others depend on: `preflight.json` (the seed), the saved blocks under `blocks/` (the fold), the schema-2 `security-findings.json` (task-review), `coverage-ledger.json` (the critic, the report, a later carry-over ticket), `SECURITY-REPORT.md` line 1 and line 2 (`run-records.mjs end`, `post-review.mjs`, the structure test), the `check-hunt.mjs` command line (the contract, the guardrail), and `judgeHunt` and the section renderer (the assembler).

## Data flow

1. STEP 0: the preflight runs with `--save` and writes `reviews/<ID>/preflight.json` when READY. STEP 0b as today: the research step's blocks go to `reviews/<ID>/research.json` before the run record.
2. STEP 1: the run record is started and read back; `check-hunt.mjs seed` writes `coverage-ledger.json` with the file and reported units; the recon step returns its block, saved as `blocks/recon.json`; `check-hunt.mjs fold` writes `architecture.md`, adds the surface units and prints wave 1's groups.
3. STEP 2, per wave: one hunter per printed group gets its lane prompt, `architecture.md`, its units and its blocks (through `check-hunt.mjs blocks`); each returned block is saved as `blocks/wave-<n>-<lane>-<k>.json`; `fold` rebuilds the ledger and lists what is open; a fresh critic's block is saved as `blocks/critic-<n>.json`; `fold` again; the next wave runs, up to wave 4.
4. STEP 3: `fold` lists the candidates, leads and hardening notes by `findingId`; verifier, batch verifier and advisory blocks are saved as `blocks/verify-<k>.json`, `blocks/batch-<lane>-<k>.json` and `blocks/advisory-<k>.json`; promoted items and new leads get single verifiers; `fold` rebuilds `security-findings.json` with every decision.
5. STEP 4: `check-hunt.mjs final` checks everything and prints the verdict.
6. STEP 5: the gatekeeper saves `blocks/run.json`; `check-hunt.mjs render` writes `SECURITY-REPORT.md`; `run-records.mjs end` removes the run record.
7. Later: task-review's assembler reads the schema-2 file through `hunt-records.mjs`; `--post` posts the report.

Stored: `reviews/<ID>/` holds `preflight.json`, `research.json`, `blocks/`, `architecture.md`, `coverage-ledger.json`, `security-findings.json`, `SECURITY-REPORT.md` and `run-log.txt`; your human partner reviews and commits them. Trust boundaries: the code under audit, its comments and its manifests are data for the recon step, the hunters, the critics and the verifiers, all inside the guardrail; the vendored blocks are third-party text whose instructions the contract overrides; the saved blocks are agent output, which the checker validates and never executes; the checker reads project files for their line counts only and prints no content; nothing crosses the network after STEP 0b except the audit tools and `gh`/`glab` reads, as today.

## Error handling

- A saved block that fails `fold`: the gatekeeper sends that agent's work back once with the findings, and saves the new block in its place; a second miss makes a hunter's lane `Declined to judge` for that group (its units stay open for the next wave) or a verifier's items `unjudged`.
- The recon step, a critic, a verifier or a batch verifier that returns no block: sent back once; then D5 (a `not-covered` surface unit per lane), the loop ends with the open units `not-covered` (critic), or the items are `unjudged` (verifiers).
- The wave limit reached: every open unit becomes `not-covered` with "wave limit reached"; the verdict cannot be PASS.
- A `HUNT-GUARDRAIL DENY` during a check: recorded as today; the unit is `blocked` with the denial as its unresolved fact.
- `seed` over the input limit, or with no `preflight.json`: the run stops before any hunter with an INCOMPLETE report that names it.
- Records that stay invalid at STEP 5: `render --incomplete "<reason>"` writes an INCOMPLETE report naming the failed check; the run record is ended as always.
- task-review with a hunt file that is not schema 2: exit 2 with the message of D10; nothing is written.
- Never silent: every `not-covered`, `blocked`, `unjudged` and declined item is named in the report, and the sentence after `Verdict:` names what decided it, including the coverage gaps and unjudged items when nothing ranks above them.
